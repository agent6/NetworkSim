# IOS FTP client teaching profile

The IOS `copy` client supports `ftp://[username[:password]@]host/path` in either direction, or `ftp:` with remote-host and filename prompts. The local endpoints are `flash:file`, `running-config`/`system:running-config`, and `startup-config`/`nvram:startup-config`. Writes ask for confirmation; cancellation opens no transfer. Configuration downloads use the existing configuration-import validation and rollback path. Text flash files and valid imported configurations persist with the lab.

The client uses the simulated TCP control connection on port 21 and a separately delivered passive TCP data connection. Authentication, disabled listeners, file permissions, routing, ACL drops and timeouts determine the result. Printed byte counts and elapsed simulation time come from the completed transaction. A rejected or interrupted transfer does not print a successful copy result.

Global configuration supports `ip ftp username`, `ip ftp password [0|7]`, `ip ftp source-interface`, and `ip ftp passive`, including bare `no` and `default` removal. Type 7 is reversible IOS-style obfuscation, not encryption. Rendered plain passwords retain safe token quoting; an imported password with conflicting quote delimiters uses a lossless Type 7 representation. Exported projects contain the lab credentials. URL credentials take precedence over configured credentials. With neither, the username is `anonymous` and the password follows the documented session-user/hostname/domain construction; an anonymous request succeeds only if the simulated server has a matching explicit account. FTP does not invent an SSH-style missing-password prompt. An up configured source interface changes the actual control/data packet source; a down interface falls back to the route-selected egress source.

This is a bounded passive IPv4 **text configuration** workflow. It does not implement active FTP, IPv6 FTP, FTPS/TLS, binary firmware images, every filesystem/VRF copy option, or a native IOS FTP server. `no ip ftp passive` restores the native configuration default of permitting connection types; this implementation still chooses passive FTP. The Server FTP form is a separate simulated service. The user-approved exclusion of Server TFTP/SCP/SFTP services and the removed Desktop File transfer UI remains in effect.

`tests/ios-ftp.test.ts` contains FTPCLI-01–07: delivered control/data channels and UTF-8 sizes; credential/render/prompt/native-alias/save-load behavior; authentication/cancellation/import rollback and invalid configuration atomicity; blocked passive data transfer; anonymous defaults and Windows Server listener state; actual source-interface/fallback packet addresses; and rendered password quoting/import roundtrips. These are executable assertions, not captured native IOS output fixtures. The separate FTP service tests exercise the server protocol and service validation.

Primary syntax and invariants were reviewed against Cisco's [IOS XE 17 configuration-file guide](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/syst-mgmt/b-system-management/m_cm-config-files-0.html), [FTP configuration command reference](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/fundamentals/command/cf_command_ref/F_through_K.html), and [`copy` command reference](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/fundamentals/command/cf_command_ref/C_commands.html). The command reference explicitly defines anonymous credential defaults, Type 0/7 syntax, no-argument removal, passive-mode permission, and source-interface fallback. Documentation review and simulator tests do not establish complete native FTP or exam equivalence.
