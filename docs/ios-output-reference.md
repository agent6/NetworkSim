# IOS-style operational output

`src/ios-show.ts` is an original, read-only presentation layer over the simulator's configuration, RIB, received protocol state, counters and forwarding resolver. It does not execute Cisco IOS. Command syntax, help and table layouts follow IOS conventions, while platform identification uses original NetSim models and NetSim OS software. Cisco copyright and licensing text is not reproduced. IOS releases and platforms differ; the linked IOS/IOS XE documentation supplies field meaning and representative layout, rather than a promise of byte-identical output for every image.

`formatIOSShow(engine, deviceId, topic, args)` takes a topic without `show`, returns lines, and returns `undefined` for topics owned by the caller. The CLI dispatches the longest recognized topic after authorization. Invalid arguments are rejected instead of silently selecting a different view. The formatter never sends packets, advances time, changes configuration or recomputes state.

## NetSim platform identities

`src/platform-identity.ts` is the shared model/software source for version, inventory, boot, configuration headers, received CDP/LLDP advertisements and SNMP system descriptions. NetSim OS uses the application version from `package.json`, not a copied Cisco release or an independently maintained firmware string.

| --- | --- | --- | --- |
| Router | `NS-R4` | 4 Gigabit | 512 MiB |
| Layer 2 switch | `NS-S24-2G` | 24 Gigabit access + 2 Gigabit uplinks | 512 MiB |
| PoE switch | `NS-S24P-2G` | 24 Gigabit access + 2 Gigabit uplinks | 512 MiB |

`show version` reports the NetSim manufacturer/model, software and bootstrap versions, embedded profile image, actual simulated hostname/uptime/restart reason, board serial, hardware revision, configured interface counts, processor/I/O memory split, flash capacity and current/next configuration register. Physical Ethernet counts exclude subinterfaces; SVIs remain separately identified as virtual Ethernet. The processor and I/O totals also back the memory commands. RAM and the 256 KiB NVRAM profile are fictional teaching specifications, not host-resource measurements or a new configuration-size enforcement limit. Flash reports the exact byte capacity used by the modeled filesystem, including a configured override.

`show inventory` uses the IOS-style `NAME`, `DESCR`, `PID`, `VID` and `SN` fields. PID is the product/model, VID `V01` is hardware revision 1.0 (not the software version), and the `NS`-prefixed serial is derived from the stable device ID. It agrees with the version command's processor board ID and survives rename, save, reload and portable lab import. These are simulated identifiers, not globally registered manufacturer serial numbers. Inventory lists the modeled fixed chassis only: it does not invent installed SFPs, modular power supplies, fans, line cards or stack members.

Boot uses the same `embedded:netsim-<kind>-<version>` profile shown by `show version`. This is embedded simulator code, not a nonexistent `flash:packages.conf` or downloadable Cisco image. Writable flash remains for user-created files; stored `boot system` choices still do not execute firmware. Existing labs retain their configurations, and both older two-part IOS-style configuration version headers and the new NetSim version headers remain importable. Neighbor views use cached received model/software advertisements rather than reading the remote device's current configuration. SNMP retains `0.0` as its unassigned vendor object identifier instead of appropriating Cisco's enterprise OID.

Before this correction, the WLC reported the router IOSv identity, all three switch kinds shared `vios_l2`, version and discovery showed different Cisco release strings, boot loaded `packages.conf` while version claimed another image, and the serial generator collided for many device IDs. The dedicated identity regressions cover those inconsistencies and read-only behavior.

Primary field references: Cisco's [show version definition](https://www.cisco.com/E-Learning/bulk/public/tac/cim/cib/using_cisco_ios_software/cmdrefs/show_version.htm) and [show inventory / PID, VID and SN definitions](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-12/command_reference/b_1712_9300_cr/interface_and_hardware_commands.html). These establish field meanings; the NetSim specifications above are deliberately original.

## Deliberate boundaries and remaining display scope

The software and hardware identity follows the NetSim policy above. Serial numbers and processor board IDs are stable per-device identifiers. Memory totals use the documented virtual profiles; CPU, memory usage and unmeasured hardware/queue/timing fields remain representative display values, not host measurements. Matching an IOS display does not make the simulator Cisco firmware or prove protocol equivalence.

* Interface, route, discovery, VLAN, STP, EtherChannel, ACL, DHCP and NAT views use local configuration and runtime state. Link and route timestamps and NAT hit/miss/expiry counters are tracked. Some hardware error counters remain idle placeholders.
* EIGRP topology includes locally originated entries derived from the same distance calculation used by DUAL, learned successors and feasible successors. Neighbor uptime, hold deadlines, message sequence and retry state are tracked; SRTT/RTO and some queue/pacing fields remain representative values. `show eigrp plugins` describes simulator capabilities rather than inventing Cisco component versions.
* OSPF displays IOS process, neighbor, interface, database, border-router, traffic and auxiliary layouts. Typed LSA sections and checksums are presentation projections of the engine's logical flooded records, not a complete wire-format, area-scoped IOS LSDB. SPF runs and packet counters are tracked; queue histories, exact LSA sizes/checksums and some timers are not. Virtual-link, event, summary-address and timer views retain simplified layouts.
* BGP stores ORIGIN, weight, candidate paths, per-type message counters and reset history, and displays gated received-routes, accepted routes and advertised-routes. State/PfxRcd counts accepted advertisements after inbound policy. Neighbor reachability is resolved from the local forwarding table, including VRF and interface state. Table version and memory use are derived display values, not IOS's monotonic revision or allocator statistics; complete queue and policy-denial measurements remain untracked.
* STP port identifiers, MST configuration/digests and instance-specific views are displayed. Port-channel switchport configuration is not automatically propagated to member ports.
* DHCP stores opaque client identifiers. It cannot turn those into an observed client MAC. Dates use the simulated clock in UTC. Pool exclusion counts union overlapping configured ranges rather than double-counting them.
* Extended traceroute prompts are not implemented. Inline traceroute options are supported; probes use the simulator's ICMP engine rather than IOS UDP traceroute. Ping repeat count is capped at 100 and timeout at 60 seconds; help advertises these implemented limits instead of larger IOS ranges. Some extended-ping IP options are unsupported.
* Commands whose operation is not simulated retain explicit `configuration stored only` notices. Running-config retains an RSA modulus command for save/replay even though IOS stores keys separately. Default log timestamps and some platform-specific messages still differ from an IOS image.
* This module covers the listed forms, not every platform-specific command or every option in Cisco's command references. Unknown options fail; they do not silently return a broad table.

## BGP compatibility behavior

The original BGP implementation now consumes default local preference (100), neighbor weight (remote default 0, local default 32768), same-neighboring-AS MED comparison, optional always-compare-med, deterministic-MED grouping, and configurable external/internal/local distance (20/200/200). Neighbor change logging is opt-in. These decisions use received UPDATE attributes and actual candidate paths. See Cisco's [MED comparison explanation](https://www.cisco.com/c/en/us/support/docs/ip/border-gateway-protocol-bgp/16046-bgp-med.html), [BGP global commands](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/iproute_bgp/command/irg-cr-book/bgp-a1.html), and [distance command](https://www.cisco.com/c/en/us/td/docs/ios/iproute_bgp/command/reference/irg_book/irg_bgp2.html).

Per-neighbor default-originate can advertise a default without a local default; its route-map condition checks the local RIB. Allowas-in admits the configured count of local-AS occurrences (default 3 when enabled). Bare remove-private-as follows the documented classic IOS all-private-path behavior, while `all` and `all replace-as` explicitly handle mixed paths. Both private ASN ranges are recognized. Raw received-routes requires soft-reconfiguration inbound; accepted and advertised views use their respective actual tables. Soft clearing recomputes retained input or resends advertisements without replacing the TCP connection. See [neighbor commands](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/iproute_bgp/command/irg-cr-book/bgp-m1.html), [allowas-in](https://www.cisco.com/c/en/us/support/docs/ip/border-gateway-protocol-bgp/112236-allowas-in-bgp-config-example.html), and [private-AS removal variants](https://www.cisco.com/c/en/us/td/docs/ios/iproute_bgp/command/reference/irg_book/irg_bgp3.html).

Password compatibility is checked on delivered SYN, SYNACK and subsequent TCP packets. A live key change updates the local connection identity; mismatched peers stop exchanging valid traffic and the existing hold timer withdraws their routes. Matching rollover before hold expiry preserves the session. The IOS command's 25-character limit applies. **This is a modeled identity check, not TCP-MD5 or cryptographic authentication.** The comparison token is not a security primitive. The actual packet channel also negotiates a 1024-byte teaching MSS, honors lower transit `ip tcp adjust-mss` values from delivered handshake packets, and segments UTF-8 messages accordingly.

Boundaries remain: the best-path model does not implement every IOS tie-break (including next-hop IGP cost and oldest external path); conditional default route-maps are conditions, not a complete default attribute transformation facility; soft input reprocessing uses retained simulator advertisements and does not send an RFC route-refresh message; peer groups, templates, dampening, add-path, confederations and multiprotocol BGP remain outside this measured wave. Ten independent compatibility tests cover policy choices, delivered AS-path changes, hold expiry, matching key rollover, render round trips, and transit MSS segmentation, in addition to the persistent-session tests.

## Community and AS-path policy closure

Reference VM probes accepted and persisted `ip bgp-community new-format`, numbered standard community lists, named expanded community expressions and an AS-path expression containing `[0-9]*`. The reference parser rejected the particular unquoted alternation expression `^(65001|65002)_[0-9]+$`; that rejection is not evidence that IOS lacks alternation. The replacement's wider matcher follows Cisco's expression semantics and uses a bounded state machine rather than JavaScript regex backtracking. Character ranges, negated classes, grouping, alternation, anchors, underscore boundaries and `*`, `+`, `?` are supported; backreferences are rejected. See [Cisco BGP expression examples](https://www.cisco.com/c/en/us/support/docs/ip/border-gateway-protocol-bgp/13754-26.html).

Community policy accepts equivalent decimal, hexadecimal and AA:NN values, plus well-known community names. Standard entries use AND within one entry and first-match ordering across entries; exact-match requires the whole set. Numbered lists 1–99 are standard and 100–500 expanded. `ip bgp-community new-format` changes display/configuration rendering and the local string matched by expanded lists; it does not alter exchanged community values. This follows the [IOS community and display command reference](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/iproute_bgp/command/irg-cr-book/bgp-c1.html). The simulator rejects a standard entry exceeding 16 communities instead of silently discarding trailing values.

The five independent tests in `tests/bgp-policy.test.ts` verify bounded matching, malformed-expression rejection, numeric equivalence, standard/exact matching, actual route installation/withdrawal when local expanded policy changes, configuration round trips, and AS-path filtering of received advertisements. BGP `community`, `community-list`, `filter-list` and `regexp` show filters use the same policy helpers. Large/extended communities, AS-set/confederation path storage and the complete IOS expression language remain outside this subset. Expressions are limited to 256 characters and matching input to 8192 characters.

## Route-map continuation and key-chain algorithm closure

The old route-map runtime explicitly enables `continue` only for BGP inbound/outbound consumers. The rewrite preserves that boundary: ordered forward jumps and implied-next continuation accumulate set actions, matching the original route attributes; later scalar actions override earlier values, community additive operations compose, and a later matched deny rejects the route. PBR, redistribution, distribute lists and default-originate retain first-match semantics. Invalid backward CLI jumps are rejected atomically. Configuration, `show route-map` and import/export preserve both continuation forms.

`cryptographic-algorithm md5|hmac-sha-1|hmac-sha-256|hmac-sha-384|hmac-sha-512` now changes OSPF key-chain identity compatibility in received Hello/exchange packets. A same-secret algorithm mismatch prevents adjacency. The OSPF sender prefers a valid key with the longest remaining send lifetime, then the highest key ID, per Cisco documentation. EIGRP/RIP retain their configured protocol authentication mode; an unrelated key-chain algorithm does not silently change MD5 to SHA. These are modeled authentication identities, not real cryptographic digest generation. Five focused tests cover delivered BGP attributes, denial and live re-evaluation, configuration round-trip, OSPF failure/recovery and protocol-specific algorithm handling.

## QoS command and packet-policy closure

The old `js/cli/commands/qos.js` accepts class descriptions, bandwidth/priority, average shape, fair queueing, RED, queue capacity, drop, and a police submode. Its `js/protocols/qos.js` runtime consumes classification, drop, marking, and policer actions; it does not consume the queue scheduler settings. The replacement preserves that distinction explicitly. Queue commands round-trip and print a configuration-only notice; show output does not invent queue depth, scheduler throughput, or congestion drops.

The original replacement policer now implements single-rate two-color or three-color byte buckets on simulation time. A three-color excess bucket receives committed-bucket overflow. Each color accepts transmit, drop, DSCP marking, or precedence marking, with actual packet/byte counts. Class-wide drop and interface/control-plane policy attachments affect delivered traffic. Class-default runs after explicit matches. The configured default burst is a bounded educational choice (at least 1500 bytes or one quarter second of rate); the model counts IP packet bytes and does not claim platform-specific Ethernet overhead accounting. Multiple simultaneous marking actions, two-rate PIR policers, hierarchical policies and real congestion scheduling remain outside this subset.

Five tests in `tests/qos-parity.test.ts` verify delivered conform/exceed/violate traffic, DSCP results and drops, nondefault color actions, excess refill ordering, precedence bit preservation, class-default fallback, CoPP isolation, atomic invalid-input rejection, prompt nesting, configuration replay, and honest show output. The QoS/core/CLI/switching/enterprise regression checkpoint passed 145 tests.

Cisco references: [policer actions and policy-map police mode](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/qos_plcshp/configuration/xe-3s/qos-plcshp-xe-3s-book/qos-plcshp-plcr-mact.html), [police and priority command forms](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/qos/command/qos-cr-book/qos-n1.html), and [queue-limit/RED command forms](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/qos/command/qos-cr-book/Q_through_R.html). Command availability and numeric ranges differ among IOS platforms; these commands describe the simulator's measured scope, not a particular Cisco image.


## BGP dampening and MSDP audit closure

Reference `js/protocols/bgp.js` retains per-prefix/per-peer flap history and exponentially decays penalty; the old command accepted dampening in both global BGP and IPv4 AF contexts. The replacement adds original external-path withdrawal tracking, configurable half-life/reuse/suppress/maximum suppression, selection suppression over retained received advertisements, timed reuse, and actual clear commands. Three tests cover delivered flaps, decay, history clearing without a TCP reset, the IPv4 unicast clear alias, iBGP exclusion and round-trip configuration. Penalty is applied on the delivered withdrawal rather than waiting for reannouncement; attribute-only penalties and route-map-specific dampening are outside this subset. See [Cisco IOS dampening commands](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/iproute_bgp/command/irg-cr-book/bgp-a1.html).

The old multicast consumer uses TCP639 for MSDP peer keepalives and Source-Active messages. `src/msdp.ts` is an original implementation using the existing loss/ACL-aware persistent TCP engine. Real RP source observation originates SA messages; received SA records enable the remote RP's source discovery and expire on simulation time. The measured peer, summary and SA-cache views expose actual connections and counters. Four network tests verify one persistent connection, SA-gated multicast delivery, blocked TCP/recovery, loss/expiry, source/RP RPF and a remote shared-tree branch. The implementation retains the old 60-second keepalive / 75-second hold behavior and periodic source advertisements. Source cache TTL is 210 seconds. Remote-AS is configuration/display metadata; the complete BGP/MBGP MSDP peer-RPF rules are not modeled. The bounded peer check admits a configured single peer or a peer on the unicast path toward the originator, with logical loop prevention.

No binary MSDP TLVs, optional encapsulated first multicast packet, mesh groups, SA request/response, filters or MD5 are claimed. Source-tree and RP shared-tree construction remain the documented computed PIM model; packet delivery still crosses actual links and checks RPF. See [Cisco MSDP transport, SA and timer behavior](https://www.cisco.com/c/en/us/td/docs/switches/lan/c9000/multicast/multicast-configuration-guide/msdp.html).
